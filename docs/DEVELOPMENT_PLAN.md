# 开发计划与模型建议

状态：M0–M1 原生主链路已实现并通过首轮测试，M2–M3 可靠性和产品体验继续完善。

## 技术决策

| 选择 | 理由 |
| --- | --- |
| macOS 14+、SwiftUI + AppKit | 当前是 Mac 场景；优先可靠的悬浮窗、菜单栏、系统通知和低常驻开销 |
| 一个应用进程 + Swift actor 调度器 | 可独立于 Codex 常驻，免去额外守护进程、Node/Python 运行环境和本地 Web 服务 |
| Foundation + URLSession + XMLParser | 原生时间、网络、RSS；缩减第三方依赖 |
| 本地 Codable JSON 原子保存 | 数据量小，首版无需数据库；版本字段、损坏隔离和备份即可 |
| UserNotifications + ServiceManagement | 本地通知和可选登录启动；免费模式不需要 X 凭据或钥匙串模块 |
| macOS 26+ Liquid Glass / 14–15 毛玻璃回退 | 原生系统玻璃，减少透明度时保持实色可读，最低系统仍为 14 |
| XCTest + 夹具回放 + 原生真机验证 | 时间、状态与去重自动验证；窗口跨桌面等体验不能只靠浏览器截图验收 |
| MIT、GitHub Actions、GitHub Releases | 开源构建和发布；不将 Actions 作为分钟级采集器 |

本次不选 Electron：此产品首要价值来自系统级窗口，原生应用更直接。暂不引入 Tauri 和 Rust/前端双栈，因为用户没有提出 Windows 首发要求；将来跨平台可以共享事件契约和测试夹具，不提前搭建平台框架。

## 分阶段实施

以下是单人熟悉 Swift/macOS、公开订阅可达时的工程时间估算，不是模型运行时长承诺。总计约 **6–11 个工程日**；签名证书等待与第三方服务故障时间另计。

| 阶段 | 任务与交付 | 验证与完成门槛 | 估算 |
| --- | --- | --- | --- |
| M0 可行性切片（已完成首轮） | 匿名读取两个社区和两个官方 feed；核对原帖链接、Atom/RSS 更新差异、缓存与上游状态；创建跨桌面 NSPanel、验证玻璃回退 | 四源匿名读取成功；原生 NSPanel、macOS 26 玻璃、折叠/迷你/双语已真机检查；全屏和多屏仍需补测 | 0.5–1 日 |
| M1 最小完整流程（已完成） | 一条明确公告→数据解析→UTC→居中弹窗→右上角→隐藏/恢复→缓存→重启 | 合成预告可端到端倒计时；事件及偏好持久化；应用独立于 Codex | 1–2 日 |
| M2 来源和时间可靠性 | RSS/Atom 稳定 ID、历史修订、跨源去重、规则分类、含糊时间、部分人群、重置机会、失败退避 | 核心时间和状态夹具全过；200 登录页、429、过期、空数据均正确处理；不漏旧条目修订、不重复弹窗 | 1.5–3 日 |
| M3 产品体验 | 折叠主窗/迷你窗、状态色与玻璃、设置和历史、浮窗内双语、时区、声音、提醒节点、登录启动、睡眠恢复 | 真机拖动/外接屏/全屏/解锁，双语 VoiceOver、音量/静音、倒计时不漂移 | 1.5–2.5 日 |
| M4 开源发布 | 精简文档、MIT、CI、构建与签名公证脚本、安装包、校验和、Release | 完整发布验收一次；干净用户环境安装启动；公开仓库无密钥和个人日志 | 1–2.5 日 |

M0 不依赖 X 账号、API 付费或私有凭据。必须验证免费订阅的实际覆盖、上游未知状态和失败退避；单次 HTTP 200 不足以证明长期完整监测。如果来源不可达，继续用夹具实现其他模块，并如实报告网络/覆盖限制。

M1–M3 每阶段按对应验收项验证即可；M4 再使用 `local-app-release-qa` 做一次实际安装发布检查。不为每个文案和样式改动重复跑整套发布流程。

## 开发交接方式

1. 先读 `PRD.md`、`IMPLEMENTATION_SPEC.md` 和 `ACCEPTANCE.md`；再打开 `design/prototype.html` 看交互。`SOURCES.md` 是事实核查入口。
2. 从 M0/M1 单个端到端流程开始；先实现时间、状态和窗口，之后增加更多公告规则。
3. 每阶段报告：实际改动、验证结果、未解决的外部依赖。演示数据与真实来源严格标注。
4. 遇到不会解析的新公告，保存最小夹具并进入待确认状态；不要为了让数字出现而猜时间。
5. 不读取 Codex 私有令牌或数据库；不创建 Codex 心跳；不增加常驻模型调用。
6. 发布版本前核对接入及签名状态。预览文件可留作设计参考，不随安装包运行。

## Astra 还是 Sol，什么 effort

**主开发推荐：GPT-5.6 Sol，effort = high。** 需求已经拆成明确契约和阶段，SwiftUI、网络适配、设置页和测试适合由同一个 Sol 开发任务连续完成，避免多个任务复制大上下文。

- 简单视觉调整、翻译和说明文档：Sol / medium。
- 日常功能、时间和调度实现：Sol / high。
- 跨应用全屏层级、睡眠恢复、时间歧义或重复提醒经过一次定位仍无明确修复：Astra / high，提供最小复现和相关文件。
- 发布前可以安排一次 Astra / high 重点审查时间、状态和原生窗口；不需要每次改动都切换。
- 不建议默认 xhigh/max/ultra；只有复杂问题在 high 下仍有未解证据才提高。

这是针对该项目的工程判断，不是已跑出的模型基准。官方比较页支持二者的能力定位与 API 单价差别；**API 单价不能直接换算成你的 ChatGPT/Codex 订阅额度消耗，也不能保证 Sol 每个任务总成本更低**。[模型比较](https://developers.openai.com/api/docs/models/compare)；[Astra 使用指南](https://developers.openai.com/api/docs/guides/latest-model)

如果只选择一个模型从头开发到完成，选 **Sol / high**。产品运行时不需要 Astra 或 Sol。
